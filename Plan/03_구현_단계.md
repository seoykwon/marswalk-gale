## 공통 규칙

- 계획·검수는 Fable, 구현은 Opus/Sonnet 서브에이전트. 판단이 많이 필요한 단계(좌표 정렬, 타일 생성기, 경로 확정, 웹 앱)는 Opus, 정해진 규칙대로 뽑고 변환하는 단계는 Sonnet.
- 원본 폴더(`MarsTrek/`, `Radiation/`, `Weather/`, `Vector/`, `Geology/`, `Photos/`, `Reference/`)는 읽기만 한다. 내려받은 파일은 실행하지 않는다. 원본을 읽는 Python은 `python3 -I`로 돌린다.
- GDAL은 `/Applications/Postgres.app/Contents/Versions/latest/bin/`의 3.8.5. Python은 표준 라이브러리만. 새 패키지 설치는 하지 않는 것을 기본으로 한다(이 계획은 설치 없이 끝까지 갈 수 있게 짰다).
- 중간 산출물은 `work/`(git 제외), 웹에 올릴 결과는 `site/`.
- 모든 가정값(속도, 경사 기준, 안테나 높이, 걸러내기 규칙)은 `scripts/config.json` 한 곳에 둔다.
- 단계마다 산출물의 개수·크기·범위·통계를 보고하고, 아래 검증 기준과 다르면 멈추고 `Plan/06_...`부터 이어서 기록한다.

## 타일화 방법 (01 문제 7의 해결)

### 비교

| 방법 | 내용 | 장점 | 단점 |
|---|---|---|---|
| ① GDAL 명령으로 직접 자르기 | `gdalwarp`로 확대 단계별 큰 그림을 타일 격자에 맞춰 만들고 `gdal_translate -srcwin`으로 256픽셀씩 잘라 저장 | 새 설치 없음. 결과가 평범한 이미지 파일이라 Leaflet 기본 기능만으로 표시. 브라우저에서 좌표 변환을 하지 않아 정렬이 단순 | 타일마다 프로세스를 띄워 느림(1만 장에 수 분, 추정). 스크립트를 직접 작성 |
| ② COG + 브라우저 라이브러리 | COG(필요한 부분만 내려받을 수 있게 배열한 GeoTIFF) 한 파일을 올리고 geotiff.js 같은 라이브러리가 조각을 읽어 그림 | 파일 하나. 원본 수치 그대로 | 파일당 100MB 제한에 걸림(CTX 1.8GB, 컬러 1GB). 화성 좌표계를 브라우저에서 처리해야 하고 라이브러리 3개가 필요. 느린 기기에서 버벅임 |
| ③ numpy/Pillow 또는 node sharp 설치 | 이미지 라이브러리로 빠르게 자르기 | 빠름 | 설치 필요. ①로 충분하면 이득이 속도뿐 |
| ④ 외부 타일만 사용 | Mars Trek 서버 호출 | 용량 0 | 서버가 내려가면 지도가 비고, 파생 레이어(경사 등)는 어차피 직접 만들어야 함 |

**추천: ①.** 고도·경사 숫자가 필요한 직접 그리기 기능(P3)은 COG 대신 작은 2진 격자 파일로 해결한다(3단계 참조). ①의 속도가 실제로 문제가 되면 그때 ③을 근거와 함께 제안한다.

### 타일 격자 규칙

- Leaflet `L.CRS.EPSG4326`의 기본 격자를 그대로 쓴다. z 단계에 가로 2^(z+1)장 × 세로 2^z장, 왼쪽 위가 (서경 180°, 북위 90°), 타일 한 장이 180/2^z 도.
- 타일 번호: `x = floor((경도+180) / (180/2^z))`, `y = floor((90−위도) / (180/2^z))`. 경로는 `tiles/<레이어>/{z}/{y}/{x}`.
- 이 규칙은 Mars Trek 타일 주소와 같다. 검산: 게일(137.4E, 4.6S)의 z=8은 x=451, y=134이고, `Vector/tile_services.md`에 기록된 표본 주소 `.../8/134/451.jpg`와 일치한다. 따라서 외부 타일은 `zoomOffset` 없이 붙는 것이 맞아 보이며, `tile_services.md`의 "zoomOffset −1" 안내는 틀렸을 가능성이 높다(01 문제 15). 5-1단계에서 브라우저로 확정한다.

### 만드는 순서 (레이어마다)

1. 원본에 공통 좌표계를 붙인 VRT(원본을 복사하지 않고 설정만 담는 가상 파일)를 만든다(1단계 산출물).
2. 확대 단계 z마다 대상 범위를 타일 경계에 맞춰 넓힌 뒤 `gdalwarp -te <범위> -ts <가로 타일 수×256> <세로 타일 수×256>`로 그 단계의 큰 그림을 `work/`에 만든다. 축소할 때는 `-r average`, 원본 해상도 이상일 때는 `-r bilinear`.
3. 큰 그림을 `gdal_translate -srcwin`으로 잘라 저장한다. `xargs -P 8`로 병렬 실행.
4. 자료가 없는 빈 타일을 지운다. 방법: 완전히 비어 있는 타일의 파일 크기를 표본으로 재고 그 크기 이하인 파일을 삭제.
5. `meta.json`에 범위, 최소·최대 확대 단계, 타일 수, 총 용량, 출처 표기를 적는다.

고배율 타일은 일부 구역에만 만든다. 지도에서는 한 레이어를 "전체를 덮는 저배율 타일층 + 구역만 덮는 고배율 타일층" 두 겹으로 묶어, 고배율이 없는 곳에서는 저배율 타일이 확대되어 보이게 한다. 고배율 구역은 사각형 4개 이하로 정한다.

### 형식

사진류(B1, B2, B4, T1, T3)는 JPEG 품질 80, 투명 배경이 필요한 것(T2, T5, T7)은 PNG. 이 GDAL에는 WebP 출력이 없다.

### 1단계. 좌표계 통일과 정렬 검증 — Opus, 2시간

배경: 원본마다 좌표계 표기가 다르다(구 / 편평한 타원체 / 지구 WGS84). 표기를 믿고 변환하면 남위 4.6°에서 위도가 약 0.054°(3km) 밀릴 수 있다(01 문제 4, 8).

1. 공통 좌표계를 `+proj=longlat +R=3396190 +no_defs`(반지름 3,396,190m 구의 경위도)로 정한다.
2. 이미 경위도인 원본(CTX, DEM, curiosity_ctx_mosaic, THEMIS 클립, TES)은 좌표 변환 없이 `gdal_translate -of VRT -a_srs`로 표기만 덮어쓴다.
3. 미터 좌표 원본(HiRISE 컬러, MOLA 463m, THEMIS 열관성·ISIS 파일)도 원본 표기를 같은 구로 덮어쓴 뒤 `gdalwarp`로 경위도로 바꾼다. 같은 구 사이라 단순 비례 변환이 된다.
4. 정렬 검증

| 검증 | 방법 | 통과 기준 |
|---|---|---|
| DEM ↔ 웨이포인트 | 웨이포인트 1,389점 위치의 DEM 값과 `elev_geoid` 비교 | 착륙지 부근(sol ≤ 400) 차이 평균의 절댓값 5m 이하. 수평으로 ±200m를 50m씩 밀었을 때 "밀지 않음"의 표준편차가 최소(개정 때 실측: 314점 표본에서 5.1m로 최소) |
| CTX ↔ DEM | DEM 범위의 CTX 위에 음영기복을 50% 투명도로 합성한 확인 그림을 3곳(착륙지, 경로 B, DEM 가장자리) 만들어 눈으로 확인 | 충돌구 테두리·능선의 어긋남이 CTX 2픽셀(10m) 이하 |
| HiRISE 컬러 ↔ 로버 경로 | 컬러 영상 위에 경로를 그린 확인 그림 | 바퀴 자국이나 지형 통로와 경로가 일치 |
| 접촉선(G2) ↔ 컬러 영상 | 같은 방식 | 지층 경계와 선이 일치. 아니면 G2 제외 |
| THEMIS·열관성 ↔ CTX | 큰 충돌구 3개의 테두리 비교 | 어긋남 2픽셀(200m) 이하 |

5. DEM과 웨이포인트의 고도 차이가 고도가 높아질수록 커지는 현상(01 문제 9)을 전체 점으로 다시 재고, 지도 표시에는 DEM 값을, 로버 지점 팝업에는 로버 기록값을 쓴다는 원칙을 확인한다.

완료 기준: `work/vrt/`에 레이어별 VRT, 확인 그림 5종, 어긋남 측정값을 Plan에 기록. **이 단계가 통과하기 전에는 경로 좌표와 타일을 확정하지 않는다.**

#### EVA 모드용 출력 보강 (+0.5시간, 09 문서 2-2절)

EVA 화면과 소매 체크리스트는 거리·시간·경사를 다시 계산하지 않고 `routes.json`을 읽기만 한다. 그래서 4단계가 아래를 함께 내야 한다.

1. 시작 전에 속도 규칙을 하나로 정한다. 02 문서 5절(5–15° 0.7배, 15–25° 0.4배, 25° 초과 통행 불가)과 `config.json`의 `walk`(`speed_factor_caution` 0.5, `speed_factor_danger` 0.25, 5° 기준 없음)가 서로 다르다. 정한 쪽으로 문서와 설정 파일을 맞추고 `routes.json`의 `meta`에 쓴 규칙을 적는다.

3. 2m 표본을 열 단위 배열로 낸다: `d_m`(누적 거리), `lon`, `lat`, `elev_m`, `slope_deg`(5m 경사 격자 값), `grade_deg`(진행 방향 기울기, 부호 있음), `vis`(가시권 0/1, T5가 없으면 생략), `t_out_s`(기지에서 그 표본까지의 누적 보행 시간), `t_ret_s`(그 표본에서 같은 길로 기지까지 돌아가는 시간).
4. EVA 지점 목록 `stations[]`: 기지·경유점·목적지 + 경사 15° 초과 구간 시작점 + 방향이 30° 이상 바뀌는 곳, 지점 간격 250m 이하(가정). 경로당 6–12개. 지점마다 좌표, 고도, 누적 거리, `t_out_s`, `t_ret_s`, 계획 체류 시간, 다음 지점까지의 구간 요약(`dist_m`, `bearing_deg`, `back_bearing_deg`, `climb_m`, `descent_m`, `time_s`, `max_slope_deg`, `len_over15_m`, `len_over25_m`, `comms_out_m`). 방위는 `atan2(Δ경도 × cos(위도), Δ위도)`, 북 기준 0–359°.
5. `hazards[]`(경사 15°/25° 초과 구간의 시작·끝 거리, 등급, 최대 경사), `comms_gaps[]`(가시권 밖 구간), `summary`(계획 모드 패널이 쓰는 합계).

| 추가 검증 | 기준 |
|---|---|
| 누적 시간 | `t_out_s`의 마지막 값 = `summary`의 편도 시간. 표본 3곳에서 구간 길이 ÷ 그 경사의 속도로 손계산한 값과 1초 이내 |
| 구간 합 | `stations[].leg.dist_m`의 합 = 편도 거리(1m 이내), `leg.time_s`의 합 = 편도 시간(1초 이내) |

| 위험 구간 | `hazards[]`의 길이 합 = `summary`의 15°/25° 초과 길이 |
| 지점 수와 용량 | 경로당 6–12개, `routes.json` 300KB 이하 |
